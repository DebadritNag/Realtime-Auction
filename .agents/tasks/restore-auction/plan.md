# Implementation Plan: Restore Auction From Snapshot

Brief: `.agents/tasks/restore-auction/brief.md` (authoritative requirements). Work is split into two sequential FEATs (backend, then frontend); FEAT files are in `.agents/tasks/restore-auction/task-restore-auction-from-snapshot/`.

## Key design decisions

**Data model (no migration, no settings-schema change).** Rooms persist as one JSON document in `public.live_room_snapshots.state`, so new optional fields on `Room` need no SQL. `settingsSchema` is `.strict()` and shared with the other two workflows, so restore data lives on `Room`, not in settings.
- `Room.restore?: { version:1; source:'TEMPLATE'|'CUSTOM'; snapshotName; snapshotHash; restoredAt; warnings:string[]; teams:{ teamId; name; purseUnits; squadSize; retainedCount; auctionCount }[] }`. This is the audit record and the authority for opening purses.
- `Team`: unchanged shape. For a restored team nobody has claimed, `userId = 'unclaimed:<teamId>'` (sentinel; unique, so the "Duplicate memberships" invariant still holds, and it never equals a real user id). Helper `isUnclaimed(team)`.
- `Team.startingBudgetUnits` = restored purse (authoritative opening balance, never derived from prices); `spentUnits` = 0 and counts only post-restore spending. `remainingBudget()` therefore equals the restored purse at start. 0 Cr team (DDD): any bid fails the existing `INSUFFICIENT_BUDGET` check.
- Each restored player is one `AuctionPlayer { status:'SOLD', restoredFromSnapshot:true, restoreSource:'FC26'|'DEFAULT_POOL'|'MANUAL' }` in `room.players`, one id in `team.playerIds`, and one `Purchase { priceUnits:0, acquisitionType:'RETENTION'|'AUCTION', isRetained, restoredFromSnapshot:true, recordedPriceUnits: 30 (15 Cr) for retained, null for auction }`. `priceUnits:0` keeps the existing ledger invariant (`sum(purchase.priceUnits) === spentUnits`) true with no new arithmetic. Prices of auction-acquired players are never required or invented (user decision).
- Remaining slots = `maxSquadSize(20) - team.playerIds.length`. The existing `validateBid` check `team.playerIds.length < maxSquadSize` and `getMaximumPermittedBid` already enforce "no buying beyond remaining slots" once squads are restored; settings force `maxSquadSize=20`, `playerPoolSource='FC26'`, `retention.enabled=false`, `numberOfTeams=teams.length`.
- Invariant changes in `assertRoom` (backend/src/modules/auction/squad.service.ts): (a) `startingBudgetUnits` must equal `room.restore` purse for restored rooms instead of `toUnits(settings.startingBudgetCr)`; (b) "Retention purchase without pick" ignores `restoredFromSnapshot` purchases.
- Locked in restored lobbies: `startingBudgetCr`, `maxSquadSize`, `numberOfTeams`, `playerPoolSource`, `retention` cannot change, and the "reset every team budget on settings update" loop is skipped (otherwise a settings PATCH would overwrite restored purses). Applies to `RoomService.updateSettings` and the engine `UPDATE_SETTINGS` case.

**Player matching** (`restore.matcher.ts`, pure, tested). Normalize names (NFD accent strip, `ø->o`, `ß->ss`, `ı->i`, punctuation to space, lowercase). Order: exact normalized `short_name` over `fc26.list()` (deduped catalog), then `long_name`; narrow multiple hits by position (snapshot position is in `positions`/`subPosition`), then club; unique -> `FC26`. Else same on the default pool CSV (`backend/data/default-pool/default-player-pool.csv`, parsed with the existing `parseCsv`) -> `DEFAULT_POOL`. `frontend/male_players.csv` (96 MB, frontend-only, not on the server) is NOT read at runtime; not a fallback. Else `AMBIGUOUS` (candidates listed) or `UNMATCHED` (top 5 surname suggestions); both are CRITICAL until the host picks a catalog player (search via existing FC26 search) or chooses "create manual player" (`id = 'manual-' + sha1(name|position)[0..12]`, flagged `MANUAL`, `ovr` default 60, min base price). Underdog flag mismatch and position mismatch vs the catalog are WARNINGS.

**Match result for the shipped snapshot (computed against the repo-root FC26 CSVs while planning).** 99/99 players match by exact short_name in the FC26 CSVs; 0 need the default-pool fallback; 0 need host resolution. The brief expected L. Messi (158023), K. Benzema (165153), M. Neuer (167495), M. ter Stegen (192448), R. Lewandowski (188545), T. Partey (209989), Alisson (212831), A. Romagnoli (210413), N. Otamendi to be missing; they are present. Repeated ids in the raw files are the same player listed in two category CSVs (catalog dedupes). The 18 snapshot "[U]" players come from `FC26_Underdogs.csv`; the coder must confirm in a test that the catalog marks them `draftPool:'UNDERDOG'` (mismatch is only a warning). Implementation still ships fallback and manual resolution (requirement 4).

**Claim / assignment rule.** Host chooses which restored team is theirs at creation (`hostTeamName`, template default `Ritzz FC`); that team gets the host's `userId`. All others are unclaimed. Join in a restored room requires `restoredTeamId` (new optional field on `joinSchema`): the server binds `userId`+`managerUsername` to that unclaimed team and ignores any submitted team name/logo (names and squads never change). One user, one team: a user who already owns a team gets their existing team back when asking for the same team (idempotent) or `409 ALREADY_CLAIMED_ANOTHER_TEAM`; an already claimed team gives `409 TEAM_ALREADY_CLAIMED`. Claims only in LOBBY (the room mutate lock serializes races). Host can release a wrong claim (`POST /api/rooms/:code/restore/release`, not their own team). In a restored room `leave` and `KICK_MEMBER` release the claim instead of deleting the team (deleting would orphan purchases and break the ledger). `START_AUCTION` is blocked with `RESTORE_TEAMS_UNCLAIMED` while any team is unclaimed (so sentinel ids never reach live bidding, skip-vote counts, or the archive). The room code is the join secret; no per-team code.

**Pot start decision.** The engine has no "start at pot X" option; `activateNext` picks a random pot with an anti-streak rule. We do NOT force "Attackers, Round 1": restored rooms use the normal order (`lastPot` unset, round 0). Documented in the final report.

**Remaining pool.** Unchanged `START_AUCTION` FC26 branch already keeps `SOLD` players in `room.players` and removes their ids from the pool, so restored players are never auctioned (also for `DEFAULT_POOL` / `MANUAL` players that are not in the catalog). The host can inspect the pool before starting via the creation preview (count + per-pot counts) and `GET /api/rooms/:code/restore/pool` (paginated, searchable, = `fc26.list()` minus owned ids, honoring `playerPoolConfig`).

**Persistence.** `RoomManager.createFromBuilder` (new method, existing `create` untouched to avoid conflicts with Part 9) calls `repository.create(room)` before the auction starts, i.e. the restored snapshot is in `live_room_snapshots` from the first commit; refresh/reconnect read it via `/state`; server restart goes through `recover()` -> `ValidatingHydrator` -> `assertRoom` with the restore rules. Nothing authoritative is in localStorage. No migration. (If ever required: additive file in `supabase/migrations/` after `20261004090000_live_room_presence.sql`; not needed.)

**Archive / Manager Mode.** `archiveCompletedAuction` reads `room.purchases`; the DB read path (`readCompletedAuction`) requires `final_price_units > 0` for owned players. Extract a pure `buildArchiveRows(room)` and, for restored purchases only, write a DB-compat placeholder (`recordedPriceUnits` or the player's base price); the full runtime snapshot with `restoredFromSnapshot` stays in `auction_runtime_snapshots`. Manual players already get a stable archive id (`stableId('auction-player:'+id)`). `ManagerModeService` uses the runtime `Room` first; restored purchases have `priceUnits:0` and `startingBudgetUnits` = restored purse (documented behavior).

**API.** `GET /api/restore/templates`, `POST /api/restore/preview`, `POST /api/restore/rooms` (all authenticated, `bodyLimit` 256 KB because the global limit is 16 KB and the 99-player snapshot is larger), `GET /api/rooms/:code` gains `restore.teams[{id,name,claimed}]`, `POST /api/rooms/:code/join` gains `restoredTeamId`, `POST /api/rooms/:code/restore/release`, `GET /api/rooms/:code/restore/pool`. `roomState` gains `restore` and per-team `claimed`, `remainingSlots`, `restoredRetainedCount`, `restoredAuctionCount`; restored `soldPlayers` carry `priceCr:null` and `restoredFromSnapshot:true`. No new WS commands or event types (`ROOM_UPDATED`, `MEMBER_JOINED`, `MEMBER_LEFT` reused). Template: `backend/data/restore/super-league-auction-2026.json`.
