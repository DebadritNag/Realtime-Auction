# Implementation Plan: 429 storm on /recommendation and false "Room does not exist"

## Root cause evidence (read from code; not yet reproduced against the hosted service)

### Why the 429 storm happens (three compounding causes)
1. **One fetch per snapshot, per client, no dedupe/cache/backoff.** `frontend/src/stores/auction.store.ts:106-112`: every `ROOM_STATE` event clears and re-arms a 350 ms timer that calls `auctionService.recommendation()` (`frontend/src/services/auction.service.ts:13`). On any failure, line 111 only sets `aiSuggestion:null`. There is no retry or backoff and no cache. The same fetch also runs on every REST/WS resync, and `initAuction` (line 76-83) fires REST `getState` plus a WS connect, which each yield a ROOM_STATE.
2. **The backend pushes a full ROOM_STATE to every subscriber on every room change.** `backend/src/realtime/hub.ts:145-156` (`broadcast` calls `sendState` for each connection after each event batch). So N clients x every bid/sale/presence-driven change = N recommendation requests per change. Each has no per-room cache: `backend/src/modules/rooms/room.routes.ts:102-106` recomputes via `DeterministicRecommendationService.recommend` on every request.
3. **The rate-limit bucket is shared by all users.** `backend/src/app.ts:48` registers `@fastify/rate-limit` with `max:120 / 1 minute`, no `keyGenerator`, so the key is `request.ip`. `backend/src/app.ts:44` sets `trustProxy:false`. On Render every request arrives from the platform proxy, so `request.ip` is the proxy address and **every client of the service shares one 120/min bucket** across all REST endpoints (state, rejoin, recommendation, results). The recommendation fan-out in (1)+(2) exhausts it quickly, so 429s hit everyone, including the authoritative `/state` calls. The 429 body is `{code:'RATE_LIMITED', message:'Request rejected.'}` (`app.ts:100-102`); the frontend ignores Retry-After (`frontend/src/services/api.ts:75-87`, `ApiError` has no retryAfter).

### Why "Room does not exist." appeared
- The exact string is produced only by `backend/src/modules/rooms/room.manager.ts:51` (`requireThat(persisted,'ROOM_NOT_FOUND','Room does not exist.',404)` inside `loadRoom`, line 43). `recommendation` (`room.routes.ts:103`), `/state`, and the WS `REJOIN_ROOM` (`hub.ts:222`) all call `loadRoom`. So a recommendation 404 with that message means the **backend itself no longer had room DGQYCD** in memory and `repository.findByCode` returned nothing. It is not a frontend misread of a recommendation 404: the recommendation `.catch` (`auction.store.ts:111`) never touches room state.
- Why the room was gone: orchestrator-verified `live_room_snapshots` has 0 rows and no `auction_rooms` row for DGQYCD, so production was not persisting live rooms. `backend/src/server.ts:80` builds `PostgresLiveRoomRepository` only when `env.STORAGE==='postgres'`; `server.ts:89` otherwise silently uses `FileRoomRepository` (ephemeral on Render) or `MemoryRoomRepository`. `env.ts:61` defaults STORAGE to `postgres` only when `NODE_ENV==='production'`. There is no log line for the non-postgres case (only `server.ts:82` logs `storage=postgres`). A Render restart/redeploy/free-tier sleep therefore wipes the room, and the next 429-recovery/recommendation/rejoin call returns a genuine 404.
- Frontend amplifiers that make a *non-room-missing* error look like "room not found" (must be fixed): `auction.store.ts:80` (REST getState failure of ANY kind, e.g. 429/500/network, stores `bidErrorNotice`), `auction.store.ts:145` (any WS `ERROR`/`BID_REJECTED` sets `bidErrorNotice`), and `frontend/src/app/room/[roomCode]/page.tsx:84-99` renders the **"Room Not Found"** ErrorState whenever `liveError`(=bidErrorNotice) is set, even when `room` is loaded. `websocket.service.ts:131` also hard-disconnects on `ROOM_NOT_FOUND`/`NOT_ROOM_MEMBER` (correct for the authoritative WS path, but there is no distinct room-missing state).
- DGQYCD cannot be recovered: 0 rows in DB. State this honestly in the report.

## Design decisions (choose one, no ambiguity for the implementer)

Backend
- Add env `TRUST_PROXY_HOPS` (int, default `1` when `NODE_ENV==='production'`, else `0`) and pass `trustProxy: hops` to Fastify at `app.ts:44`. Reason: Render always fronts the service with one proxy; this makes the limiter key the real client IP. Do not use `trustProxy:true` (spoofable).
- Keep global `max:120/min`. Add a route-level limit on the recommendation route: `config:{rateLimit:{max:60,timeWindow:'1 minute'}}` with `keyGenerator` = bearer-token-hash? Simplest correct: keyGenerator `${request.ip}:${userId}` is not available before auth, so key on `request.ip` only, with the proxy fix in place. Add `errorResponseBuilder` returning `statusCode:429`, `code:'RATE_LIMITED'`, and ensure the `Retry-After` header (seconds) is present on every 429; extend the `app.ts:99-102` handler to set `retry-after` from `error.retryAfter`/existing header and include `retryAfterSeconds` in the JSON error body. Log rate-limit events with `app.log.warn({eventType:'RATE_LIMITED', route, ip-hash-free})`, never tokens/headers. Add `onExceeded`/`onExceeding` hook (or log in the handler).
- Recommendation cache: in `room.routes.ts` keep a `Map<string,{key,promise|value}>` keyed by `roomCode:userTeamId`, validated by `room.sequence` + `room.active?.playerId` (and the user's remaining budget is part of the sequence). Concurrent calls for the same key share one in-flight promise; evict on key change and cap map size. The route must still enforce `requireMember` before returning cached data (no cross-team leak: key includes team id).
- Error codes: recommendation route returns 404 `ROOM_NOT_FOUND` only from `loadRoom`; when the room exists but there is no active player return **200**-compatible `409 RECOMMENDATION_UNAVAILABLE` (status 409, code `RECOMMENDATION_UNAVAILABLE`) instead of an undefined `playerId` response; check `recommendation.service.ts` first to see what it does with `room.active===null` (read it and keep existing behavior if it already throws a typed error; do not add new rules beyond that).
- Storage: in `server.ts` log `[auction] storage=<postgres|file|memory> nodeEnv=<..>` for every case. In `readEnvironment`, when `NODE_ENV==='production'` and `STORAGE` is `file` or `memory`, throw unless `ALLOW_EPHEMERAL_STORAGE==='true'` (new optional env); error message names the variable. If the escape hatch is used, `server.ts` logs `console.error('[auction] WARNING: live rooms are ephemeral ...')`. Check existing env tests (`grep readEnvironment backend/tests`) so none that set production+file break.

Frontend
- New module `recommendation.service.ts` exporting a singleton `recommendationFetcher` with `request(roomCode, {sequence, playerId})`, `cancel()`, `reset()`. Behavior: cache keyed `roomCode:playerId:bidTeam-agnostic?` — key = `roomCode|activationId|sequence`; only one in-flight request (reuse promise for same key; `AbortController` abort when key changes); response applied only if key still current (stale responses ignored). Trigger on activePlayer change (`playerChanged` in `auction.store.ts:98`) and on `currentBid` change using a **leading+trailing debounce of 1.5 s**, not every snapshot; ROOM_STATE with an unchanged `activationId` and unchanged `currentBidCr` must not fetch. Identical key + cached value inside the same sequence: no network call.
- 429: read `Retry-After` (seconds or HTTP date) into `ApiError.retryAfterMs`; wait `max(retryAfter, 1000*2^n)` plus jitter (0-25%), max 3 automatic retries total across the shared fetcher, then set `recommendationStatus:'unavailable'`; a new key resets the counter. 404/409/5xx/network/timeout: `unavailable` with no retry for 404/409, one delayed retry for 5xx/network. 401/403: mark unavailable, no retry (auth refresh stays in `api.ts`/`refreshAuth`).
- Stop on `leaveAuction` and when `snapshot.status!=='RUNNING'` (cancel timers and abort).
- Panel shows "Recommendations temporarily unavailable" (no error styling that blocks bidding); never sets `bidErrorNotice`.
- Room-missing: add `roomMissing` state. `auction.store.ts:80` catch: `ApiError.status===404 && code==='ROOM_NOT_FOUND'` sets `roomMissing:true`; any other error keeps existing snapshot, sets a non-blocking `syncNotice`, and schedules one shared retry of `roomService.getState` using the same backoff helper (cap 5). WS `ERROR` with `reason==='ROOM_NOT_FOUND'` sets `roomMissing:true`; other ERROR events do not affect room display. `room/[roomCode]/page.tsx:94` must key the "Room Not Found" screen off `roomMissing || (error && !room)`, never off `liveError` alone.
- Reconnect/state sync: the existing reconnect (`websocket.service.ts:94-148`, backoff `backoffDelay` line 10, REJOIN_ROOM on open line 112, SYNCED only after ROOM_STATE line 123) already re-syncs; write tests proving it (same room, no duplicate membership, timer from `endsAt`) and change code only if a test fails.
- Room-state completeness (item 6): `roomState()` is in `backend/src/modules/rooms/room.state.ts` (find with grep). Add a backend test asserting presence of the required fields (status, retention, activity, recentBids, purses, squads, soldPlayers, unsoldPlayers, endsAt, queue position). Fill gaps from existing model only; if none are missing, change nothing.

## Test list (all offline; no hosted DB)
Backend (vitest, use `backend/tests/helpers.ts`, `helpers-pg-double.ts`, patterns in `continue-rejoin.test.ts`, `restart-recovery.test.ts`):
- 429 carries `Retry-After` and `RATE_LIMITED` body; limiter keys distinct clients with `trustProxy` + `X-Forwarded-For`.
- Recommendation cache: N concurrent requests -> `recommend` called once; new sequence -> recomputed; other team does not get cached value.
- Missing room -> 404 `ROOM_NOT_FOUND`; no active player -> `RECOMMENDATION_UNAVAILABLE`.
- `readEnvironment`: production + STORAGE unset -> `postgres`; production + file/memory -> throws; escape hatch allowed.
- Restart simulation: with durable repo, new manager instance returns same room/state (extend `restart-recovery.test.ts` pattern).
Frontend (node .mjs esbuild harness as in `tests/api-client.mjs`, `tests/reconnect-protocol.mjs`):
- Fetch count bounded across 50 ROOM_STATE events with the same activation/bid (1 call), +1 per new bid/player.
- 429 with Retry-After -> waits, capped retries (<=3), then unavailable; store snapshot/timer/bids untouched.
- Recommendation 404/500/network -> `roomMissing` stays false, no redirect, snapshot intact.
- REST `/state` 404 `ROOM_NOT_FOUND` -> `roomMissing:true`; `/state` 429/500/network -> snapshot preserved, retry scheduled.
- Disconnect/reconnect -> same room, REJOIN_ROOM sent, ROOM_STATE applied, no duplicate participants/events.
