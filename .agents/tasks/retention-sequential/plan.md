## 1. What exists today (read, not assumed)

- **Retention is a free-for-all sub-phase of LOBBY** inside the `Room` aggregate. `Room.retention = { phase: 'OPEN'|'FINALIZED', picks, finalizedAt }` (`domain/types.ts`). `retainPlayer` (`modules/retention/retention.service.ts`) immediately writes a `Purchase` (30 units, `acquisitionType:'RETENTION'`), `team.spentUnits += 30`, `team.playerIds.push`, and a SOLD `room.players` entry. `assertRoom` (`squad.service.ts` lines 39-56) ties every pick to a purchase.
- **Commands** (`auction.engine.ts`, `auction.schemas.ts`): `RETAIN_PLAYER {playerId}` is a member-level branch before the host-only `else`. `FINALIZE_RETENTIONS` and `RESET_RETENTIONS` are host cases. `START_AUCTION` throws `RETENTION_NOT_FINALIZED` while `retentionPhase(room)==='OPEN'`. Events today: `PLAYER_RETAINED`, `RETENTION_FINALIZED`, `RETENTION_RESET`.
- **Real-time:** one mechanism. `RoomManager.mutate` commits, then `hub.broadcast` sends every event and then a per-connection `ROOM_STATE` built by `roomState(room, userId, ...)` (`room-state.ts`). Because `roomState` takes the viewer's `userId`, per-viewer redaction is possible without a second channel. `REJOIN_ROOM`/`REQUEST_STATE` return the latest `ROOM_STATE`.
- **Auth model:** every team has `userId`; `requireMember(room, userId)` resolves the acting team; the host is `room.hostUserId` and also owns a team. WebSocket auth is per user (`AuthContext`). So per-manager auth already exists. There is no shared-device mode and none is added.
- **Persistence:** room file snapshot is authoritative (CAS on `sequence`). `PostgresRetentionLedger` (`retention.ledger.ts`) mirrors picks into `auction_retentions` (write-behind, errors swallowed and logged). It fires on events whose type is in `RETENTION_EVENT_TYPES` (`app.ts` line 61).
- **Frontend:** retention UI is embedded in the lobby page (`app/room/[roomCode]/page.tsx` renders `<RetentionScreen/>`), with `components/retention/{RetentionScreen,RetentionTeamSwitcher,RetentionFilters,RetentionPlayerCard,RetainedPlayersPanel,FinalizeRetentionsDialog}.tsx`, `services/retention.service.ts`, and `tests/retention-ui.mjs` (esbuild bundle + chromium, drives `RetentionScreen` with a stubbed `webSocketService.send`). The live auction page is `app/auction/[roomCode]/page.tsx` + `auction.css` (routes use the **room code**, not an auction id). `soldPlayers` in `ROOM_STATE` already carries `acquisitionType`/`isRetained`. The store (`stores/auction.store.ts`) treats `ROOM_STATE` as authoritative and feeds `recentBids` from `BID_UPDATED`.
- **Baseline (from the prior review, not re-run in this step):** backend `tsc` passes; vitest has 6 known failures (5 in `tests/skip-vote.test.ts`, 1 skip-vote case in `tests/integration.test.ts`) plus load-only timeouts in cups/manager-mode that pass alone.

## 2. Decisions

**D1. Auth model: per-manager auth, with host as fallback. No new login.**
- Retention commands are accepted from the **active team's own manager**. The server resolves the acting team from `userId` and compares it with `retention.activeTeamId`. The client never names the team for authorization. Any other member gets `NOT_ACTIVE_TEAM` (403/409), and a command that arrives after the turn ended gets `TURN_ALREADY_COMPLETED`.
- The **host** has two extra, explicit powers: `START_RETENTION` and `SKIP_RETENTION` on behalf of the active team (escape hatch for an absent manager; the skip discards that team's draft and records `confirmedBy = host`). The host cannot select or confirm players for another team, so the host never needs to see another team's draft. That keeps unconfirmed picks private (Part 2 requirement) and avoids a "host impersonates manager" path.
- Host is also a team. When the host's own team is active it acts through the same manager path.
- **"Continue to Next Team":** not a gate. The backend advances automatically on confirm or skip (spec: "automatically advances"). Gating on a host click would stall every handover on one person, and with per-manager auth nobody needs a device handover. The handover screen (retention page, shown to the team that just finished) and the global announcement overlay (all clients) show "TEAM N - RETENTION COMPLETE ... NEXT UP". The action buttons on the handover screen are real and role-based: the next team's manager sees "Start your selection" only once they are active; the host sees "Skip this turn" for the active team. No placeholder "Continue" button is shipped. This is a recorded deviation from "Continue to Next Team where the host-controlled workflow requires it": the workflow here does not require it. `TEAM_COMPLETED` is represented as the per-turn status plus `lastCompleted`, not as a blocking room phase.

**D2. State machine** (stored in `Room.retention`, persisted in the room snapshot, so refresh/reconnect never resets it):
```
phase: 'NOT_STARTED' | 'TEAM_SELECTING' | 'ALL_TEAMS_COMPLETED' | 'FINALIZED'
order: string[]            // team ids, frozen at START_RETENTION in room.teams order (Team 1..N)
activeTeamId: string|null  // only set in TEAM_SELECTING
turns: RetentionTurn[]     // completed turns; id is the announcement event id
drafts: RetentionDraft[]   // unconfirmed selections {teamId, playerId, snapshot, at}
picks: RetentionPick[]     // confirmed picks (+ turnId, order, snapshot, confirmedAt, confirmedBy)
finalizedAt?: number
```
- `RetentionTurn = { id: uuid, teamId, order, kind: 'RETAINED'|'SKIPPED', playerIds, spentUnits, remainingUnits, nextTeamId|null, allCompleted, at, confirmedBy }`.
- `RetentionPick` gains `turnId`, `order` (1-based retention_order), `confirmedAt`, `confirmedBy` and `snapshot` (name, fullName, ovr, position, subPosition, club, nationality, image URL, playerTag, draftPool). The snapshot makes announcements and the retained-players list independent of the catalog and of `room.players`.
- `TEAM_COMPLETED` is derived (`turns.at(-1)` while the phase is still `TEAM_SELECTING`), see D1.
- Legacy normalization in `ValidatingHydrator.hydrate` (`room.manager.ts`): phase `'OPEN'` becomes `NOT_STARTED`. Legacy `'OPEN'` picks already have purchases; convert them into drafts of their team using the existing `removePicks` (which reverses purchase, spend, squad id and SOLD entry), so no money is lost and nothing needs a fake turn. Legacy `'FINALIZED'` stays `FINALIZED`; its picks are materialized, and missing `turns` is allowed (the state exposes synthesized read-only summaries). A rooms without `retention` or with the setting off still gets `OFF`.

**D3. Money and squads apply at finalize, not at pick time.**
- Confirm only records picks. Draft and confirmed picks deduct nothing from `team.spentUnits` and add nothing to `room.purchases`/`room.players`/`team.playerIds`. They are tracked in `retention`.
- `FINALIZE_RETENTIONS` (host, phase `ALL_TEAMS_COMPLETED`) materializes every confirmed pick in one `mutate` commit: `Purchase {priceUnits:30, acquisitionType:'RETENTION', isRetained:true, bidCount:0, durationMs:0}`, `team.spentUnits += 30`, `team.playerIds.push`, a SOLD `room.players` entry (base price recomputed by `fc26BasePriceUnits`), phase `FINALIZED`. Result for start 200: teams with 0, 1, 2, 3 picks end at remaining 200, 185, 170, 155.
- During selection the visible remaining purse is computed as `startingBudgetUnits - spentUnits - confirmedPickSpend` (and minus the viewer's own draft for the selecting team). `publicTeam` already receives `room.retention` and computes `retentionSpentCr`/`auctionPurseCr`; extend it to count only confirmed picks before finalize.
- Why: the brief says squads, purses and acquisition records change on finalize; nothing about an unconfirmed or unfinalized pick then leaks through `players`, `soldPlayers`, `team.playerIds` or `spentCr` in the shared `ROOM_STATE`; `assertRoom` stays simple (pick/purchase tie enforced only when `FINALIZED`). Cost: `assertRoom`, `removePicks` and the existing `retention.test.ts` cases change.
- `RESET_RETENTIONS` (host, LOBBY): if `FINALIZED`, reverses the materialization (existing `removePicks`); always clears drafts, picks and turns and returns to `NOT_STARTED`. Allowed only while `room.status==='LOBBY'`.

**D4. Commands** (all through `commandSchema` + `AuctionEngine.execute`, so they get `requestId` idempotency, `expectedSequence`, the per-room lock and a CAS commit):
- `START_RETENTION` (host): LOBBY, retention enabled, phase `NOT_STARTED`, FC26 catalog available, at least `minimumParticipants` teams. Sets `order`, `activeTeamId = order[0]`, phase `TEAM_SELECTING`.
- `RETAIN_PLAYER {playerId}` (keeps its name; now adds a **draft**): requires acting team == `activeTeamId`, then in order: player exists in the FC26 catalog (`RETENTION_PLAYER_NOT_FOUND`), not confirmed by anyone (`PLAYER_ALREADY_RETAINED`), not in anyone's draft (`PLAYER_RESERVED`; already in own draft is idempotent no-op rejected as `ALREADY_SELECTED`), confirmed+draft count < 3 (`RETENTION_LIMIT_REACHED`), squad size (`SQUAD_FULL`), purse >= 15 Cr per player (`INSUFFICIENT_PURSE`).
- `REMOVE_RETENTION_PLAYER {playerId}` (new): active team removes its own draft.
- `CONFIRM_RETENTION` (new): active team, 1 to 3 drafts. Moves drafts to confirmed picks, appends a `RetentionTurn`, advances to the next team or to `ALL_TEAMS_COMPLETED`. Zero drafts is rejected with `USE_SKIP_RETENTION` (explicit skip rule).
- `SKIP_RETENTION` (new): active team's manager, or the host on its behalf. Discards drafts, appends a `SKIPPED` turn, advances.
- `FINALIZE_RETENTIONS` (host): phase must be `ALL_TEAMS_COMPLETED` (`RETENTION_NOT_COMPLETE` otherwise). `RESET_RETENTIONS` (host) as in D3.
- Out-of-order protection is structural: the target team is derived on the server; no `teamId` is trusted. A second confirm after the turn advanced fails because the actor is no longer active (`NOT_ACTIVE_TEAM`) or the phase is not `TEAM_SELECTING`. The DB mirror also has `unique(room_id, team_id)` on turns (D6).
- `START_AUCTION` gate becomes: if retention enabled, phase must be `FINALIZED` (`RETENTION_NOT_FINALIZED`). Retention OFF is the unchanged path. Join/leave/kick: allowed only in `NOT_STARTED`; once started, membership changes are rejected with `RETENTION_IN_PROGRESS` (409) until the host resets. `UPDATE_SETTINGS` locks purse/source/retention flag once the phase is not `NOT_STARTED` (`assertRetentionSettingsUnlocked`).
- Each handler stays in `retention.service.ts` as a pure function on the draft room (the existing style); the engine only wires commands and builds events.

**D5. Real-time events** (same WebSocket, `RoomManager` events, nothing new). Names follow the existing UPPER_SNAKE convention; the issue's suggested names map as follows:

| retention.started | `RETENTION_STARTED` | `{order:[{teamId,name,order}], activeTeamId}` |

| finalized | `RETENTION_FINALIZED` (existing) | existing plus `finalizedAt` |
| (reset) | `RETENTION_RESET` (existing) | existing |

- `RETENTION_TEAM_CONFIRMED` payload: `{eventId (= turn.id), kind, teamId, teamName, teamOrder, totalTeams, players:[{playerId,name,fullName,ovr,position,subPosition,club,nationality,imageUrl,playerTag,priceCr}], spentCr, remainingPurseCr, nextTeamId, nextTeamName, nextTeamOrder, allCompleted, at}`. The old `PLAYER_RETAINED` is dropped (nothing shipped on it; frontend mapping is updated). Add the new names to `RETENTION_EVENT_TYPES` in `retention.ledger.ts` and to the frontend `names` list in `types/backend.ts`.
- **Unique event id per turn** is the turn's uuid, created once under the room lock, so a retried command (same `requestId`, idempotent receipt) cannot produce a second one.
- **Persisted announcement data:** the `turns` array in `Room.retention` is exposed in `ROOM_STATE.retention.turns` (completed turns only, same shape as the payload; for `ALL_COMPLETED` the overview is derived). A reconnecting client gets correct status from `ROOM_STATE` and decides what to show with its seen-set (D9).
- **Privacy of `ROOM_STATE`** (`retentionState()` in `room-state.ts`): `reservedPlayerIds` (all drafts, no owner) goes to everyone; `ownDraft` (full snapshots) only to the viewer whose team is the draft owner; `picks`/`turns` are confirmed only. Nobody else ever receives another team's draft contents or owner. Events carry draft data to nobody except the owner's own `ROOM_STATE`.
- The catalog route `GET /api/rooms/:code/retention/players` (in `fc26.routes.ts`) excludes confirmed picks and others' drafts, and marks the viewer's own drafts `selected:true`. It is member-only.

## 4. Risks and how the plan handles them

- **Rewriting a committed, reviewed service.** The pure-function style, error codes, `mutate` locking, ledger and hydrator are kept. `removePicks` (reverse of materialization) is reused for reset and legacy conversion.
- **Privacy leak through `ROOM_STATE`.** Drafts are the only unconfirmed data. They live in `retention.drafts` (not in `players`, `purchases`, `playerIds`), and `retentionState()` is the single place that exposes them, per viewer. A backend test asserts it.
- **Duplicate overlay after refresh.** Seen-set in `localStorage` plus the 15 s freshness rule and the server `turns` list (D9). Frontend test replays an event and a state.
- **Host-skip abuse/disconnect stall.** The host skip is audited through `confirmedBy` and the turn record, and uses the same code path.
- **The redesign touching the live bidding path.** No store selector or bid handler is removed; tabs hide rather than unmount; existing UI tests are re-run in item 12.
